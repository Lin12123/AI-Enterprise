# API Executor Architecture

## Status

- implemented: legacy VBA compatibility flow remains available through the fixed `macros/AI_Enterprise_Runner.bas`; current API executor implements PRD P0 atomic operations, MVP composite operations, and the 14 requested P1 operations behind explicit confirmation.
- scaffolded: P2/P3 feature families such as revolve, sweep, loft, shell, rib, draft, advanced mirror/body pattern operations, broader reference geometry, and advanced surface/body features.
- planned: broader official SOLIDWORKS API coverage beyond the current P0 scope.

## Target Flow

Natural language -> CADPlan or FeaturePlan -> validator / Policy Engine -> fixed API Executor -> SOLIDWORKS API.

LLM and Codex output must stay declarative. They may produce CADPlan or FeaturePlan data, but they must not directly control SOLIDWORKS or generate executable runtime code.

## Executor Boundary

`src/solidworks_api/executor.py` validates FeaturePlan input and can produce a dry-run trace without connecting to SOLIDWORKS. Confirmed real execution connects only to an already-open SOLIDWORKS instance.

Current executable API operations include PRD P0 atomic operations, the 14 requested P1 operations, and the older MVP composite operations: `create_base_plate`, `cut_corner_holes`, `create_center_boss`, and `cut_center_hole`.

## Operation Planning

Before dry-run output or real API execution, the executor runs a fixed operation planner. The planner keeps the LLM output declarative and handles safe ordering rules inside the trusted executor boundary.

Current planning rules include:

- `create_new_part` runs before modeling operations when present.
- `create_base_plate` runs before base-dependent operations such as corner holes, center boss, and center hole.
- `create_center_boss` runs before `cut_center_hole` when `target` is `boss`.
- rebuild/validation operations run after modeling operations.
- output operations run after modeling and validation operations.

Future feature additions must declare their executor-side dependencies in this planning layer. The executor should reorder safe independent operations before drawing instead of waiting for avoidable feature-order errors. If a dependency cannot be satisfied because the required operation is absent, the planner must block before real drawing begins.

SOLIDWORKS face selection may still fail because of COM state, model rebuild timing, or version-specific selection behavior. Face selectors should retry after a controlled rebuild when safe, then fail with a clear error only if the planned geometry still cannot be selected.

## SOLIDWORKS COM Compatibility

SOLIDWORKS 2019 SP5 COM calls can reject otherwise documented calls because of optional-argument handling, selection marks, empty string references, or version-specific method overloads. Fixed executor code must not rely on a single unguarded COM signature for high-risk APIs.

For version-sensitive calls, use the compatibility helpers in `src/solidworks_api/com_compat.py`:

- try a controlled list of method/signature candidates;
- capture every failed candidate in the diagnostic message;
- use safe selection helpers before feature creation;
- prefer deterministic executor geometry for simple, fully understood features when native COM pattern calls are unstable;
- keep fallback behavior documented in the capability matrix and cookbook.

Fallbacks must stay inside the fixed executor and must not be generated by the LLM. A fallback may only be used when it preserves the declared FeaturePlan operation semantics within a documented limitation. If the operation cannot be safely represented, the executor must fail clearly instead of silently producing unrelated geometry.

Real execution must:

- require a passed Policy Engine result;
- use only Feature Registry allowlisted operations;
- keep outputs under controlled workspace directories;
- avoid user-defined output directories;
- never execute generated Python, VBA, C#, PowerShell, Shell, macro, or script code.
- require explicit user confirmation before connecting to SOLIDWORKS.

## pywin32

pywin32 is not installed or invoked automatically. If a future phase uses COM automation, the user must install pywin32 manually in the chosen Python environment.
